Project 04: Inside the Boundary, On the Record

Measured results, reproducible from one command

What would it take to say yes to AI on customer data?

Banks, insurers, retailers, telecoms, hospitals and governments all want the same AI models, and are stopped by the same three questions: where does the personal information go, who can prove what was sent, and what stops a team overspending. This gateway answers all three in the one place every request passes through. It replaces personal details with placeholders before a request leaves and puts them back in the answer, it refuses to send data where the policy says it may not go, it writes every call into a record that cannot be quietly changed, and it enforces each team's budget before the call, not after the invoice. Every one of those costs time, so the cost is measured and published too.

The meeting that stops AI adoption

The technology is rarely what stops a bank, an insurer, a retailer, a hospital or a government department from using AI. A meeting is. Privacy, audit and finance each ask a question, and in most organisations nobody can answer, because the plumbing to answer it was never built.

It speaks the same protocol as the AI vendors, so an existing application moves onto it by changing one address and one key, and every project in this portfolio that calls a model already calls it through this gateway's library.

One request, in eight steps

The order is the design. The record is written before anything leaves, so a call that crashes halfway is still on the books, and every refusal happens before the network is touched.

  1. 1DeclareThe caller says what class of data this is. Saying nothing counts as personal.
  2. 2ScreenFlag text that looks like an attempt to hijack the model.
  3. 3RedactSwap names and numbers for placeholders, and refuse if any is left.
  4. 4RouteSend only to a provider and region the policy allows for this data.
  5. 5BudgetRefuse if the worst-case cost would pass the team's limit.
  6. 6RecordWrite the ledger row, before anything is sent.
  7. 7SendCall the vendor, and put the real values back into the answer.
  8. 8SealChain the finished row into the audit record, anchored daily in public.

This is a real run of the gateway's redaction engine, the one the live server uses, on a made-up request. The vendor receives placeholders, writes its answer in placeholders, and the person asking gets the real values back. Nobody here exists.

It fails closed. Without a language model it recognises only {{recall_rules}} of the details on its own, and still nothing leaks, because a second pass masks whatever it cannot vouch for and the gateway refuses to send text it cannot vouch for. The price is masking too much, and on real text that price is high.

For the technical reader: two passes, three corpora, and the limitation measured
  • Detection, then a guard. Rule-based recognisers (Canadian SIN with its checksum, provincial health numbers, postal codes, phone numbers, email, file numbers) find spans; a second pass masks capitalised runs and identifier-shaped tokens the vocabulary does not excuse; outbound refuses any text in which a value or a shape survives. Detector recall alone is {{recall_rules}}; the leak rate after the guard is {{leak_rate}}.
  • Through the proxy, over HTTP. 200 generated pages holding {{wire_values}} planted values, sent as personal, plain and streamed, to an upstream that parses what it received. A value counts as leaked if it is there whole or any three of its digits are. The run is repeated with redaction off and must find every value, so the zero could have said otherwise.
  • On real text. On the Text Anonymization Benchmark's court judgments it masks {{tab_direct}} of direct identifiers, but its precision is {{tab_precision}} and it touches {{tab_safe}} of the spans annotators marked safe, because its vocabulary is Canadian and knows nothing of British courts. An allow list derived from the benchmark's training split takes that to {{tab_safe_allow}}. A deployment in another jurisdiction has to supply its own.
  • Reversible, and scoped. Placeholders are consistent within a request and put back on the way out, tolerant of the ways models rewrite them. Only values the caller's own messages carried are put back, for the reason in What did not work.
  • Every figure, per entity type, with Wilson intervals: docs/redact.md.

Where a request may go

Every request carries a class: public, internal, personal or sensitive. The policy says which providers and regions each class may reach, and the gateway refuses the rest before anything is sent. This grid is computed from the live configuration by the same function the gateway calls; point at a cell for the reason.

{{residency_grid}}

The policy is the Canadian worked example, written to show the refusal. Unredacted personal data may go only where single-region processing in Canada can be declared, and no hosted vendor here can declare it, so only the local model qualifies. Once the gateway has redacted it, a personal request is judged as internal data and may reach a provider with a declared residency, such as Claude on Amazon Bedrock in Canada.

{{policy_sent}} of {{policy_forbidden}}forbidden requests sent, on the adversarial suite through every way of calling the library, 95% interval {{policy_ci}}
{{policy_refused_n}}allowed requests wrongly refused; a policy that refused everything would score perfectly on the first number, so this one stands beside it
{{policy_audited_n}}refusals on the record: a refusal is a call, so it is written down too
For the technical reader: declared, never inferred, and never measured
  • The class is declared by the caller and never guessed from content. A gateway that classified data itself would be making a compliance judgement no human signed. An absent declaration is personal, so a forgetful caller is refused rather than exposed.
  • Residency is the operator's declaration on each provider entry. Not one of the vendors reports where a request was actually processed, so the gateway enforces a declaration and says so, rather than presenting it as a measurement.
  • The expected answer comes from an oracle that reads the policy file as plain data and shares no code with the engine. Through the proxy over HTTP: {{policy_proxy}}.
  • docs/policy.md and the policy file.

A record nobody can quietly change

Every call is written into a chain: each record carries a fingerprint of the one before it, so changing any old record breaks every record after it. Once a day the chain's newest fingerprint is published in the public repository, so even the organisation running the gateway cannot rewrite its own history without it showing.

{{tamper_found}} of {{tamper_tried}}rewrites caught before the last anchor, across {{tamper_kinds}} kinds, 95% interval {{tamper_ci}}
{{false_alarms_n}}false alarms on records nobody touched, 95% interval {{false_alarms_ci}}
{{verify_ms}}to check a {{verify_records}}-record chain from end to end

After the last anchor, a competent forger wins, and the page says so. Of rewrites made after the last published fingerprint, {{after_anchor}}. No hash chain can do better: there is nothing yet to disagree with. That window is one day, which is why the anchor is published daily.

For the technical reader: what the chain proves, and what it cannot
  • The tamper test corrupts a 500-record chain anchored every 50 records, 200 times per kind, from a careless edit to a forger who owns every file, recomputes every hash and edits the ledger to agree.
  • Append-only by grant, not only by trigger. On the live server the proxy's database role can add records and cannot change or delete one, and a trigger refuses changes for the owner too.
  • The anchor is a GitHub Action that reads /audit/head every morning and commits it to anchors/gateway.jsonl, refusing a sequence that goes backwards or a sequence whose fingerprint changed.
  • An intact chain does not prove the ledger recorded every call; the completeness test in Budgets is that claim. docs/audit.md.

Budgets that refuse before the call

Each team has a monthly budget, and the public demo key a daily one. Before a request is sent, the gateway adds a deliberately pessimistic estimate of its cost to what the team has spent, and refuses if the total would pass the limit. Cost comes from the token counts the vendor returns and a dated price list; a model with no known price is recorded as uncosted, never guessed.

{{caps_reached}} of {{caps_attempted}}calls attempted past a spending cap that reached the vendor
{{fidelity_n}}measurement calls sent byte for byte as built, with no retry, cache or rewrite
{{lib_p50}}the library's own cost per call at the median ({{lib_p50_ci}}), against a vendor that answers instantly

The record survives a crash. {{complete_n}} calls left a ledger row under fault injection, {{complete_across}}.

For the technical reader: why the row is written before the call
  • The usual order loses exactly the calls that matter. Logging after the reply means the only calls that go unrecorded are the ones that crashed, timed out or were killed. Here the row is written before sending, holding its estimate against the budget, and completed after.
  • One step for every worker. The hosted gateway runs four processes; the cap check and the row it admits are one call to a function in Postgres under an advisory lock, so two workers cannot both pass a cap only one fits under. A test sends twelve calls at once at a cap that fits three, and three go through.
  • The vendor's own console cap is the first line of defence, outside this code. A budget whose only enforcement is the code that might have the bug is not a budget.

What it costs in time

Every control adds delay. Measured on the server that runs the gateway, against a stand-in vendor that always takes 50 ms, with the controls switched on one at a time, at 50, 200 and 500 requests a second: the extra time the gateway adds, five runs each, with a 95% interval across runs.

{{load_failed}} of {{load_requests}}requests failed, across every layer and load
{{audit500_p99}} msat the 99th percentile at 500 a second, with the record on ({{audit500_ci}})
{{red200_p99}} mswith redaction too, at 200 a second ({{red200_ci}})
{{red500_p50}} msmedian with redaction at 500 a second: a queue, at the edge of what four shared cores can redact

Each measurement changed the design. The first run stopped at 200 requests a second because the record was written on the request path; moving it off fixed that. A later run blamed the server for failures at 500, and was wrong: the workers had processor time to spare and were queued on the budget check's lock. That check is now a single call inside the database, and every request is answered.

For the technical reader: method, and what the profile found
  • Method. k6 at a constant arrival rate, so a slow answer never slows the next request; overhead is the gateway's percentile minus the stand-in's in the same run; a run whose baseline shows a pause on the host is dropped and counted. The server is a 4 vCPU, 8 GB VPS in Beauharnois, Quebec, shared by the generator, the stand-in, four gateway workers, Postgres and Redis.
  • The lock. Postgres showed three workers waiting on the admission lock while the fourth held it idle between round trips. One function call in the database took routing at 500 a second from about 13% failed to none.
  • A profile under load found four more costs: threads queued on one database connection, the HTTP client's pool walking every connection on each request, a Redis call blocking the event loop, and a missing package that turned an import inside every lock into a search of the disk.
  • The cache sheds rather than queues. Embedding a question costs about 19 ms of a core whatever the batch, so past what the server can embed, a request goes upstream as if the cache were off, and says so. Those cells report how many were shed instead of a figure.
  • docs/loadtest.md, with every run since the first.

Does redaction make the answers worse?

The question a buyer asks second, and almost never hears answered. Measured with project 03's release gate, the portfolio's measuring instrument: the same questions with and without redaction, paired, across three models, and judged by 03's own calibrated judge.

{{quality_effect}}points of complete answers, redacted against raw, over {{quality_pairs}} pairs; no loss on any answerable question
{{distractor_effect}}points less often does a redacted request say "this page does not cover that" when handed the wrong page
{{redteam_vendor}}confidential values reaching the vendor under attack, where one model leaked {{redteam_llama_raw}} unredacted

The real cost is in retrieval. Given a page that cannot answer the question, a redacted model is more likely to answer from memory than to say so. For a pipeline that sometimes fetches the wrong document, that is the case that matters, and it is reported as the result rather than averaged away.

Answers from memory, with the risk beside the saving

Repeated questions can be answered from a store of earlier answers, at no cost. The risk is answering a slightly different question with the confidence of an exact match, so the false-hit rate is published beside the hit rate, and the cache is switched off for personal and sensitive data entirely.

{{cache_hits_n}}reworded questions found in the cache, {{cache_hits_rest}}
{{cache_false_n}}of those hits were the wrong question, {{cache_false_rest}}
{{cache_retrieval_false}}wrong hits when a question sits inside a long retrieved page, so those are never cached
{{cache_redacted_false}}wrong hits on redacted requests, whose placeholders make every customer look alike
For the technical reader: what goes in, and the injection screen beside it
  • Only a bare question the caller marks (X-Boundary-Cache: question), one store per team, never personal, sensitive, redacted, flagged or streamed, and only a complete answer is stored. The threshold, 0.82, was chosen on one half of the questions and committed before the other half ran.
  • The injection screen catches {{screen_train}} of attacks on the set its rules were written on and {{screen_heldout}} on held-out ones; it caught {{screen_templated}} of project 03's templated attacks and flagged {{screen_overrefusal}} ordinary prompts. It flags by default rather than blocking, because blocking's false-positive cost belongs to the policy owner. docs/screen.md, docs/cache.md.

What did not work

Putting every value back into the answer. The first design restored every placeholder in the vendor's reply, including values that came from the application's own instructions rather than from the person asking. Under 03's red team, one model refused every attempt to extract a confidential record, listing the placeholders it would not share, and the gateway then helpfully filled them in: {{redteam_haiku_full}} attacks succeeded through the gateway that had failed against the model. Restoring only the values the caller sent took that to {{redteam_haiku_scoped}}, and it is now the default.

What this does not do

It does not decide what is sensitive

The caller declares the class and the gateway enforces the policy for that declaration. Guessing would be a compliance judgement nobody signed.

It cannot verify where a vendor processed a request

No vendor reports it. The gateway enforces the operator's declaration and says that is what it is.

Redaction over-masks on real text

{{tab_safe}} of safe words touched on court judgments with its Canadian vocabulary. A deployment elsewhere supplies its own allow list.

Text only

Images and audio cannot be redacted here, so they are refused for anything but public data.

One server, one region

Residency here controls where requests may go, not where the gateway runs. It is one 4 vCPU host, and redaction at 500 a second is at its edge.

The cache's saving is not yet measured

What it saves depends on how often real traffic repeats, which needs a replay of real traffic with hand-labelled hits.

For the technical reader: the rules the code enforces on itself
  • Pass-through mode is inviolable. No retries, no cache, no rewriting; a test compares the bytes handed to the HTTP client with the bytes the adapter built.
  • No content in telemetry. The fields a span may carry are listed in code, and attaching anything else raises.
  • No vendor SDKs. Plain HTTP with pinned API version headers, because an SDK's changed default is a silent edit to a measurement.
  • Never guess a price. An unknown price writes an uncosted row; it never writes an estimate.
  • Every reported number carries an interval, and every table is written by the command that measured it. This page reads those tables, so it cannot disagree with them.

Glossary
Anchor
The newest fingerprint of the audit chain, published somewhere the operator cannot edit, here a public repository, once a day.
Confidence interval
The range a measured rate would plausibly fall in if the measurement were repeated. A bare number without one is treated as a defect here.
Data class
What a request says it carries: public, internal, personal or sensitive. It decides where the request may go.
Hash chain
A list of records in which each carries a fingerprint of the one before, so changing an old record breaks every later fingerprint.
Percentile
The 99th percentile is the delay that 99 requests in 100 stay under: it describes the slow requests, which the median hides.
Placeholder
A typed stand-in such as <PHONE_1> that replaces a personal detail on the way out and is swapped back on the way in.
Residency
Where a provider declares it processes data: in one region, in a group of countries, or anywhere.
SHA-256
A fingerprint of a piece of data. Change one character and the fingerprint changes completely.
